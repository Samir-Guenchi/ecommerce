\chapter{Introduction}

\section{Purpose}

This document provides comprehensive technical documentation for the Algérie Poste E-Commerce database. It is intended for:

\begin{itemize}
    \item Backend developers implementing API features
    \item Database administrators managing the production environment
    \item New team members onboarding to the project
    \item Auditors reviewing data architecture
\end{itemize}

\section{Scope}

The database supports a multi-vendor e-commerce marketplace with the following key features:

\begin{enumerate}
    \item \textbf{Multi-vendor Marketplace} -- Multiple sellers with individual storefronts
    \item \textbf{Escrow Payment System} -- Secure buyer protection with fund holding
    \item \textbf{Hybrid Tracking} -- Algérie Poste API + internal last-mile tracking
    \item \textbf{Home Delivery} -- Courier management with GPS tracking
    \item \textbf{OTP Verification} -- Secure package handoff confirmation
\end{enumerate}

\section{Module Descriptions}

\subsection{Users Module}
Handles user accounts, authentication, addresses, and seller verification.

\begin{itemize}
    \item \texttt{users} -- Central user accounts
    \item \texttt{user\_addresses} -- Shipping/billing addresses
    \item \texttt{seller\_registrations} -- Seller verification documents
\end{itemize}

\subsection{Commerce Module}
Manages stores, products, categories, and reviews.

\begin{itemize}
    \item \texttt{stores} -- Seller storefronts
    \item \texttt{products} -- Product catalog
    \item \texttt{categories} -- Hierarchical categories
    \item \texttt{reviews} -- Product reviews
\end{itemize}

\subsection{Orders Module}
Handles order lifecycle from cart to delivery.

\begin{itemize}
    \item \texttt{orders} -- Customer orders
    \item \texttt{order\_items} -- Line items with snapshots
\end{itemize}

\subsection{Payments Module}
Manages payment transactions and escrow accounts.

\begin{itemize}
    \item \texttt{payments} -- Payment transactions
    \item \texttt{escrow\_accounts} -- Fund holding
    \item \texttt{disputes} -- Payment disputes
\end{itemize}

\subsection{Logistics Module}
Handles shipping with hybrid tracking (Algérie Poste + last-mile).

\begin{itemize}
    \item \texttt{shipments} -- Shipping records
    \item \texttt{tracking\_events} -- Tracking history
    \item \texttt{couriers} -- Delivery personnel
    \item \texttt{courier\_assignments} -- Delivery assignments
    \item \texttt{delivery\_zones} -- Geographic zones
    \item \texttt{delivery\_ratings} -- Courier ratings
\end{itemize}

\subsection{Reference Data}
Static reference tables.

\begin{itemize}
    \item \texttt{wilayas} -- 58 Algerian provinces
    \item \texttt{themes} -- Store themes
    \item \texttt{plans} -- Subscription plans
\end{itemize}

\chapter{Normalization Analysis}

\section{Normal Forms Applied}

The database schema adheres to the following normal forms:

\subsection{First Normal Form (1NF)}

\textbf{Requirements:}
\begin{itemize}
    \item All tables have a primary key
    \item All columns contain atomic values
    \item No repeating groups
\end{itemize}

\textbf{Status:} $\checkmark$ All tables satisfy 1NF, with documented exceptions for JSON fields used for flexibility (images, attributes, addresses).

\subsection{Second Normal Form (2NF)}

\textbf{Requirements:}
\begin{itemize}
    \item Must satisfy 1NF
    \item No partial dependencies on composite keys
\end{itemize}

\textbf{Status:} $\checkmark$ All tables use single-column primary keys, eliminating partial dependencies.

\subsection{Third Normal Form (3NF)}

\textbf{Requirements:}
\begin{itemize}
    \item Must satisfy 2NF
    \item No transitive dependencies
\end{itemize}

\textbf{Status:} $\checkmark$ Most tables satisfy 3NF. Intentional denormalizations are documented.

\section{Intentional Denormalizations}

\subsection{Product Snapshots in Order Items}

\textbf{Fields:} \texttt{product\_name}, \texttt{product\_price}, \texttt{product\_snapshot}

\textbf{Justification:}
\begin{itemize}
    \item Products may be renamed or deleted after order
    \item Prices may change
    \item Legal requirement to preserve original transaction details
    \item Common e-commerce pattern (Amazon, Shopify)
\end{itemize}

\subsection{Address Snapshots in Orders}

\textbf{Fields:} \texttt{shipping\_address} (JSON), \texttt{billing\_address} (JSON)

\textbf{Justification:}
\begin{itemize}
    \item User may modify or delete addresses after order
    \item Historical orders must show original delivery location
    \item Immutability requirement for audit trails
\end{itemize}

\subsection{Derived Fields in Products}

\textbf{Fields:} \texttt{rating}, \texttt{review\_count}

\textbf{Calculation:}
\begin{align}
    rating &= \text{AVG}(\text{reviews.rating}) \\
    review\_count &= \text{COUNT}(\text{reviews})
\end{align}

\textbf{Justification:}
\begin{itemize}
    \item Avoids expensive JOIN on every product listing
    \item Updated via application logic when reviews change
\end{itemize}

\chapter{Indexes and Performance}

\section{Index Strategy}

\subsection{Primary Indexes}
All tables use auto-increment integer primary keys for optimal JOIN performance.

\subsection{Unique Indexes}
\begin{itemize}
    \item \texttt{users.email} -- Fast login lookup
    \item \texttt{products.slug} -- URL routing
    \item \texttt{orders.order\_number} -- Customer-facing lookup
    \item \texttt{shipments.tracking\_number} -- Tracking queries
\end{itemize}

\subsection{Foreign Key Indexes}
Explicit indexes are created for foreign key columns to optimize JOIN performance.

\subsection{Composite Indexes}

\begin{lstlisting}[caption=Key Composite Indexes]
-- Products by store and status
CREATE INDEX idx_products_store_status 
  ON products(store_id, status);

-- Orders by buyer and status
CREATE INDEX idx_orders_buyer_status 
  ON orders(buyer_id, status);

-- Shipments awaiting delivery
CREATE INDEX idx_shipments_delivery_pending 
  ON shipments(status, delivery_type);

-- Tracking events by shipment and time
CREATE INDEX idx_tracking_shipment_time 
  ON tracking_events(shipment_id, event_time DESC);
\end{lstlisting}

\section{Query Optimization Tips}

\begin{enumerate}
    \item Use \texttt{EXPLAIN} to analyze query plans
    \item Avoid \texttt{SELECT *} -- specify needed columns
    \item Use pagination with \texttt{LIMIT} and \texttt{OFFSET}
    \item Cache derived data (product ratings)
    \item Use connection pooling (TypeORM default)
\end{enumerate}

\chapter{Security Considerations}

\section{Data Protection}

\subsection{Password Storage}
Passwords are hashed using bcrypt with salt rounds of 12:

\begin{lstlisting}[language=TypeScript, caption=Password Hashing Example]
import * as bcrypt from 'bcrypt';

const saltRounds = 12;
const hash = await bcrypt.hash(password, saltRounds);
\end{lstlisting}

\subsection{Sensitive Data}
\begin{itemize}
    \item \texttt{password\_hash} -- Never exposed via API
    \item \texttt{ssid}, \texttt{cnrc\_number} -- Seller documents, admin-only access
    \item \texttt{ccp\_account} -- Payment info, encrypted at rest
\end{itemize}

\section{Access Control}

Row-level security is implemented at the application layer:

\begin{itemize}
    \item Buyers can only view their own orders
    \item Sellers can only view their store's orders
    \item Couriers can only view assigned shipments
    \item Admins have full access with audit logging
\end{itemize}

\section{Audit Trail}

The \texttt{audit\_logs} table records all sensitive operations:

\begin{lstlisting}[caption=Audit Log Structure]
audit_logs (
  user_id     -- Who performed the action
  action      -- CREATE, UPDATE, DELETE
  entity_type -- 'order', 'payment', etc.
  entity_id   -- Affected record ID
  old_values  -- JSON of previous state
  new_values  -- JSON of new state
  ip_address  -- Request IP
  user_agent  -- Browser/client info
  created_at  -- Timestamp
)
\end{lstlisting}

\chapter{Backup and Recovery}

\section{Backup Strategy}

\subsection{Full Backup}

\begin{lstlisting}[language=bash, caption=Full Database Backup]
pg_dump -U postgres \
  -d ap_ecommerce \
  -F c \
  -f backup_$(date +%Y%m%d_%H%M%S).dump
\end{lstlisting}

\subsection{Incremental Backup}

Enable WAL archiving for point-in-time recovery:

\begin{lstlisting}[caption=PostgreSQL WAL Configuration]
# postgresql.conf
archive_mode = on
archive_command = 'cp %p /archive/%f'
wal_level = replica
\end{lstlisting}

\section{Recovery Procedures}

\subsection{Full Restore}

\begin{lstlisting}[language=bash, caption=Database Restore]
pg_restore -U postgres \
  -d ap_ecommerce \
  -c backup_20251206.dump
\end{lstlisting}

\subsection{Point-in-Time Recovery}

\begin{lstlisting}[language=bash, caption=Point-in-Time Recovery]
# In recovery.conf or postgresql.auto.conf
restore_command = 'cp /archive/%f %p'
recovery_target_time = '2025-12-06 14:00:00'
\end{lstlisting}
